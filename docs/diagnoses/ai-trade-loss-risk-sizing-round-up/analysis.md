# AI 自动交易持续亏损：风控仓位被档位取整抬高

## 一、问题描述

**已确认一个可独立复现的 P1 风控缺陷：仓位求解器算出的风险上限，
会被后续“就近吸附到仓位档位”突破。** 以本机会话配置构造的离线断面中，求解器要求
40% 仓位、200 USDT 名义额，最终却允许 50%、250 USDT，超限 25%。
这个问题会放大不利交易的敞口和费用，修复目标应是恢复风险上限约束。

本次确认的是可放大亏损的风控缺陷，尚未量化它对历史亏损的贡献；
**不能据此断言它解释全部亏损，
也不能断言修复后策略盈利**。最新分组确有本地账面亏损，但所有成交腿
的费用仍为估算，交易所结算对账覆盖不完整。

## 二、复现步骤

### 2.1 离线最小复现：不需要账户、网络或桌面程序

前提：已安装项目后端依赖，本机现有 `services/quant/.venv` 可直接运行。
在 PowerShell 逐行执行：

```powershell

services/quant/.venv/Scripts/python.exe -B -X utf8 docs/diagnoses/ai-trade-loss-risk-sizing-round-up/repro_sizing.py --output docs/diagnoses/ai-trade-loss-risk-sizing-round-up/repro-results.json
```

脚本使用当前业务类 `SizingRuntime`、`GroupExposureBook` 和
`TradeDecision`，输入半仓提议、500 USDT 满仓名义额、200 USDT
有效敞口上限。合成价格序列只用于离线输入夹具，不用于评价策略收益。
无需 mock 求解函数，也无需修改业务代码。

观察首个用例：

```text

下单名义额 = 250.0 > 敞口上限 200.0
```

**预期行为：** 最终风险仓位不能超过连续求解上限；若合法档位中
没有满足风险约束的正仓位，则返回 `hold`。本例唯一正档位为 50%、
100%，均不满足 40% 上限，因此应 `hold`。

## 三、根因分析与证据

### 3.1 已确认根因：风险求解后复用了会向上取整的模型档位函数

数据流及具体落点如下：

1. **分组生成敞口上限。**
   `services/quant/app/ai_auto/manager.py:792` 将
   `total * leverage / member_count` 作为 `unit_notional`。
   本机为 `100 * 5 / 5 = 100`；balanced 的倍数为 2，
   `services/quant/app/ai_auto/exposure_book.py:139` 得到上限 200。
   `max_ratio` 下成员可用满仓名义额仍为 `100 * 5 = 500`。
   该组合使最低 50% 档位本身就高于此时单个空仓成员可用的敞口上限。
2. **连续求解确实正确缩小。**
   `services/quant/app/ai_auto/sizing_runtime.py:349` 先求初值，
   `:382` 将提议名义额传入共享敞口簿，`:351` 按缩减系数重新求解。
   `services/quant/app/ai_auto/exposure_book.py:48` 解二次不等式，
   空仓本例求得 0.8；`services/quant/app/ai_auto/sizing.py:417`
   计算 `f_raw = min(entry, f_core) * brake * corr = 0.4`。
3. **正数结果没有受最终上限保护。**
   `services/quant/app/ai_auto/sizing.py:452` 只对零解直接否决，
   `:454` 的低档判据依赖 `floor_ratio`。
   `services/quant/app/config.py:1341` 默认开启零解否决，
   `:1345` 的 `floor_ratio` 默认是 0，所以 0.4 不会被拦截。
4. **随后向上抬回最低档。**
   `services/quant/app/ai_auto/sizing.py:431` 调用
   `quantize_size_fraction(f_raw, step)`。
   `services/quant/app/ai_auto/signals.py:676` 的函数本来用于模型提议，
   `:694` 执行 `max(1, min(round(lo / step), len(ladder)))`，
   将 0.4 / 0.5 吸附到 0.5。这里没有“最终值 ≤ 风险解”的约束。
5. **记录抵消后继续执行。**
   `services/quant/app/ai_auto/sizing.py:432` 仅计算 `scale_erased`；
   `services/quant/app/ai_auto/sizing_runtime.py:400` 仅累计计数，
   `:293` 仍将最终占比写入决策。
   `services/quant/app/ai_auto/session.py:3688` 接收该结果；
   `services/quant/app/live_auto/executor.py:1480` 按
   `strength * budget_usd * leverage` 计算名义额，再取交易所张数步长。

核心代码摘录：

```python
# services/quant/app/ai_auto/sizing.py:417
f_raw = min(entry, f_core) * brake * corr
# services/quant/app/ai_auto/sizing.py:431
fraction = quantize_size_fraction(f_raw, inputs.step)
# services/quant/app/ai_auto/signals.py:694
gears = max(1, min(round(lo / step), len(ladder)))
```

因此边界错误在“**连续风险解 → 最终离散仓位**”，无需猜测模型能力，
也不需要真实行情跌涨才能触发。

### 3.3 亏损的其他观察与证据限制

**① 本次亏损不能简化为费用漏算或 1m 高频。** 最新会话是 30m，
费用非零，毛额也为负；旧文档的“1m 周期、手续费恒零”不能直接套用。

**② 8 笔开仓全部走共识逆势通路。** 这里的 `contrarian` 指共识门禁
的特殊通路，不等于每笔都逆着价格趋势。
`services/quant/app/ai_auto/gear_resolution.py:158` 的 `downgrade_one_gear`
及其最低档分支允许 `floor_is_min` 保持最低档；这是当前明确设计，
不能当作新发现的“降档代码没执行”。它与粗档位、后置风险取整叠加，
让实际小额试探空间有限。8 个样本不足以证明该通路总体无效。

**③ edge 放行不等于正期望证明。** 最新分组的 edge 统计累计
236 次 pass、0 次 veto、3 次 unavailable。已配对成交的估算来源为 ATR。
`services/quant/app/ai_auto/edge_gate.py:113` 起先把 ATR 幅度作为分子，
`:148` 比较 `edge >= k * cost`；没有绑定经校准先验时，波动幅度本身
不提供方向胜率。它不能保证交易赚到这个幅度。
这属于收益模型与标定的后续问题，不能用提高自报置信度阈值来宣称已修复。

**④ 利润保护本会话未装配。** 保存配置为 `profitGuard=null`；
`services/quant/app/ai_auto/profit_guard_runtime.py:157` 在规则缺席时早退。
BTC 平仓 51221 的 `peak_pnl=2.0274`、最终净额 -0.25075001，
说明有浮盈回吐观察。关闭保护是配置事实；没有报价路径回放，不能计算
“开启后一定能保住多少利润”，也不应自行替用户修改该配置。

**⑤ 经济反馈尚非完整实测。**
`services/quant/app/live_auto/executor.py:889` 的主动平仓结算仍先使用
`ref_px` 计算，`:894` 写入成交；应结合实测成交与结算补齐再验证。
本机 `economics.basis=local_estimate`，相关成员的交易所比较覆盖不完整。
这限制精确损失归因，但不影响对本地仓位上限被突破的判定。

**⑥ 网络异常及生命周期不一致是独立观察，尚未建立亏损因果。**

## 四、影响面

- 已开启仓位管理且使用离散档位的 AI 自动交易，尤其是粗档位、
  多标的共享预算、相关性敞口缩减和回撤减仓场景。
- 任何正数风险解都可能被向上吸附：包括波动率、凯利、相关性或刹车
  产生的解。它会破坏风险求解约束；本次实际证明的是敞口上限。
- 共用 `resolve_size_fraction` 的回测也应纳入修复验证。
- `hold`、`close`、撤单和未开启仓位层的分支应保留原行为。
- 连续档位避开本次取整缺陷；细档位只能降低误差，不能提供上限保证。
- 本报告未审计全部历史会话、账户全部交易，也未验证当前桌面安装包
  是否等于源码版本；不能把这一分组的 8 笔交易推广为所有用户的表现。

## 五、候选修复方案对比

| 方案 | 内容 | 侵入程度 | 风险 / 局限 | 预估工作量 |
|---|---|---|---|---|
| **A：最终仓位受风险解与敞口双重约束** | 仓位层选择不超过连续解的合法档位；无正档可行则 hold；按最终提交量与分组占用复核敞口 | 核心集中于 sizing/runtime；提交保护涉及会话、执行器和分组敞口簿 | 开仓数可能下降；旧吸附断言需调整；必须覆盖对冲、数值精度及在途委托 | 原估 1–2 工程日仅供参考；须计入提交及挂单生命周期回归后重估 |

## 六、推荐方案及理由

**推荐 A。** 它直接修复“求解后破坏上限”的确定性错误，不需要
重新训练模型、调整盈利阈值或改变交易方向规则。

建议后续实现边界：

1. 保留 `signals.quantize_size_fraction` 对模型提议的既有用途；在风险
   求解出口建立专用的保守档位选择，避免全局改动影响模型 schema。
2. 保证 `final_fraction <= f_raw`，以未作展示舍入的风险解为准，
   且不把正数小解或零解抬高。
   最低档不可行时通过现有 hold/原因码/漏斗路径呈现一次明确拒绝。
3. **按最终可执行量重新检查有效敞口。** 多空对冲中，缩小某一腿并不
   总使组合风险下降，不能只依赖“向下取整”；应在候选合法档位中验证
   全部约束，无可行解则拒绝新增仓位。交易所张数取整后的量也需满足约束。
4. 在实际提交边界使用最新共享敞口状态复核，并保证检查与分组风险占用
   原子完成。评审已确认存在跨 `await` 窗口和挂单不计入当前名义额的
   路径，见 8.3；未复现历史并发成交，不将其列作已证实的亏损根因。
5. 用本报告 6 个断面及零解、正常合法档、多空对冲、close 豁免、
   真实张数步长补回归；保证实盘与回测使用同一风险约束。
6. 生效配置仍允许粗档位，但应显示“最小档超过风险上限，暂不建仓”的

   要求交易所回读数量与原委托数量一致。若在元数据加载、价格取整或限流
   等待之后再修改该数量，会破坏同一订单身份的恢复契约。因此在持久化
   之前逐档选择实际张数并同步占用；持久化之后继续复核，数量或风险条件
   不再满足时以 `sizing_exposure_cap` 明确拒绝本次未发送委托，不改写或重发
   该身份。后续正常决策可以重新求解。此策略可能比即时重建订单更保守。
2. **实际发送点比执行器入口更深。** `okx/trading.py` 会重新加载合约
   元数据、取价格并设置杠杆；`okx/trade_client.py` 还会等待限流和连接池。
   修复在这些等待结束后、调用 HTTP 发送之前，按最终请求体的张数、合约
   面值与价格同步复核。市价基准为这次服务调用取得的报价；不保证未知
   成交价或后续行情变化后的敞口恒定。
3. **旧恢复记录可能没有可靠的提交名义额。** 新订单把 `riskNotionalCap`
   写入现有 pending 的订单字段，并随既有 adoptedOrder 转存。旧记录缺失
   此字段时，不能用历史未取整限价或当前预算猜测上限；该未决订单在身份
   核实、成交或撤销前阻止分组新增风险。没有另建持久化账本或数据库表。
4. **在途订单不能获得已成交对冲的抵扣。** 对每个未完成开仓使用“当前
   持仓到可能全部成交”的名义额区间，按各二次型项的区间最大值计算保守
   上界。固定持仓仍按带符号相关性计算；部分成交转入持仓，余单继续占用。
   此实现复杂度为 O(n²)，可能拒绝一些实际可行的组合，但不会把尚未成交
   的对冲当作可用风险额度。二次型比较只允许 16 ULP 的机器误差（USD²），
   请求体序列化比较只允许 8 ULP（张数或 USD），不使用展示舍入值判安全。
5. **回测下一根撮合还会重新计算权益。** 仅修改决策占比仍可能在权益上涨
   后突破原名义额上限。回测订单现在携带决策时的名义额上限与档位步长，
   撮合新增腿时复用同一保守取档函数；价格或数量无效时不成交。独立平仓
   及反手中的平仓腿继续执行。回测未装配完整分组状态，不据此宣称验证了
   实盘分组的全部风险。

3. **保留不确定状态并修复反手误拒。** 取消或超时不会释放退出腿的不确定
   状态；撤余单也不证明旧持仓仍完整。现有平仓账本没有逐笔采纳部分平仓
