## 一、交互现状诊断

统计页的卡片顺序本身已经是一条因果叙事，源码注释写得很明确：纪律卡紧跟 KPI，因为「AI 为什么开单变少」是用户看完收益数字后的第一个问题（`AiTradeStatsLive.tsx:184-186`）；可交易性与漏斗紧跟纪律卡，因为「AI 为什么不开单」的完整答案要这三张卡连起来读（`:202-204`）。

### 1.2 缺口

**缺口一：档位阈值没有来历。** 只读阈值表给出十五行数字与中文标签，全部由后端下发（`discipline.py:125-127` 明确要求前端不复制任何一个）。但没有任何一处告诉用户这些数字从哪来。`discipline.py:36` 的自陈只存在于源码注释里。

**缺口二：运行期没有「换周期」的落点。** 启动前的路径是完整的，`firstFeasibleAlternative`（`aiTradeTradability.ts:106-113`）会挑出第一个非 `infeasible` 的更长周期，`PickBarButton` 把它渲染成一个按钮。但这个函数今天只有一个消费者（`AiTradeTradabilityFields.tsx:267`）。会话跑起来之后，`TradabilityCard` 显示的是启动时的断面且刻意不刷新（`TradabilityCard.tsx:9-10` 说明了理由），`tradabilitySummary`（`:70-77`）只在 `infeasible` 时返回一句话。用户在跑了两百轮零开仓之后，界面上没有一个可以点的东西。

**缺口三：三个问题分在两个标签里。** 「我现在赚不赚钱」的池化答案在「历史」标签（`AiTradeStatsHistoryList.tsx:52-56` 的三张卡），「为什么没开仓」与「这个周期值不值得做」在「当前」标签（`AiTradeStatsLive.tsx:187-209`）。两组读数的口径还不一样：可交易性卡的否决率分母是窗口内全部 K 线断面，漏斗的分母是模型真的提出过的开仓意图数，`TradabilityCard.tsx:12-14` 已经把这个口径差写成了必须说明的事项。

**缺口四：配置面窄，但窄在哪里必须说准。** `AiTradeLaunchModal.tsx` 有 1578 行，其中 `<label>` 标签实测 14 处（数法：正则 `<label` 计数；多数是包裹式、无独立文本）。

启动请求本身并不窄。`AiTradeGroupStartIn`（`schemas.py:840-882`）共 20 个顶层字段，其中最后四个是成组的行为块：`baseRules`（内嵌 MA 通道）、`profitGuard`（12 字段）、`tradingHorizon`（11 字段）、`discipline`（10 字段）。本次用 pydantic 的 `model_fields` 逐一清点，四个块计在这 20 个之内。窄的是**改写 settings 的那条路**：四块里只有 `discipline` 走 `model_copy` 派生会话副本，且只覆盖 8 个阈值键（`discipline.py:109-118`）；另外三块由 `_resolve_base_rules` / `_resolve_profit_guard` / `_resolve_horizon` 解析成规则对象，默认值取自 `ai_trade_*` 却不改写 settings，因此它们改的是本会话的规则、不是配置项。这两条路之外的 `ai_trade_*`，唯一入口是改 `agent.env`：桌面端 prod 按 `AI_TRADE_` 等前缀透传（`desktop/src/lib/config.js:74-82`），未在 `config.py` 里声明的键会被 `Settings` 的 `extra="ignore"` 静默丢弃（`config.js:67-73` 为这个坑写过警告，仓库为它栽过两次）。

**做产品排期时要分清这两类。** 「加一个界面入口」对第一类（settings 副本键）意味着扩 `AiTradeDisciplineIn` 与冻结表的分工，对第二类（规则对象字段）意味着在弹窗里多渲染一个已经存在的入参，成本差一个量级。

## 二、档位的可解释性

**目标是给既有四档补来历，不动档位本身。** 中文档位名沿用既有 UI 用词：稳健 / 均衡 / 激进 / 关闭（前端 `aiTradeDiscipline.ts:36-52`，后端 `discipline.py:121-123`，两处已经一致，不得另造第三套）。

**每档需要补的三件事**：

1. **开了哪几项。** 这里涉及两张不同的表，别混：运行期的纪律自检 wire 是 **13 行**（`discipline_view.py:23-25` 的 `ROW_KEYS`），弹窗的只读阈值表是 **15 行**（`preset_rows`）。13 行那张已经带 `armed` 与 `note`，`armed=false` 时 `note` 必填（`schemas.py:835`）；15 行那张今天只显示阈值。把前者的汇总（`已生效 N/13`，`aiTradeDiscipline.ts:74`）放到弹窗上即可。不要试图把两张表合成一张，它们的行集与作用域都不同。
2. **阈值多少与预期副作用。** 阈值已有。副作用需要新增一句由后端下发的文案，例如 `k_min` 那一行补「提高它会让开单变少，在短周期上尤其明显」。文案由后端产出的理由与阈值相同：前端抄一份，下次调参时就会静默分叉（`discipline.py:125-127`）。
3. **这些数字尚未标定。** 这是本节的核心要求。在阈值表的表头位置放一句固定文案：「这组数字由默认成本断面与 ATR 粗估推演而来，尚未经过回测校准」。措辞与 `discipline.py:36` 的自陈一致，**不得美化**。等 [02 号 §二](./02-calibration-and-activation.md) 的标定记录落地之后，逐行替换为「已按 <日期> 的 <样本量> 笔往返标定」。

**渐进披露**：默认只显示档位卡与一句后果说明（今天已经是这样）；展开才显示十五行阈值；再展开才显示每一行的标定状态与依据。三层结构的理由是绝大多数用户只需要第一层，而需要第三层的人一定会去找它。

**涉及真实资金的操作必须二次确认。** 现有的确认点是可交易性判定为 `infeasible` 时的那一行勾选（`AiTradeTradabilityFields.tsx:284-310`），它的设计有两条值得沿用：启动按钮**永不禁用**（`:27-28` 写明「只提示、不阻断」，本仓库四次「永不开单」事故都源于把不确定翻译成否决）；确认态在 `level` 由非 `infeasible` 变为 `infeasible` 的跃迁时必须重置（`:30-32`），否则用户在 A 周期上确认过的风险会被静默套用到 B 周期。**逐字段覆盖阈值时需要新增一个同形状的确认**，因为那是绕过冻结表直接改门禁的操作。

## 三、一屏答清三个问题

**定义**：「盈利体检首屏」是统计页的第一屏，用户打开后三秒内应当读到三个问题的结论，且每个结论都能接一个动作。

| 问题 | 结论该显示什么 | 数据来源 | 可接的动作 |
|---|---|---|---|
| **我现在赚不赚钱** | 净额盈亏、往返笔数、显著性结论三者同屏 | `ai_auto/profitability.py` 经 `GET /ai-trade/history/profitability` | 样本不足时展开看还差多少笔 |
| **为什么没开仓** | 从开仓意图到成交的闭合漏斗，点名首拦截层 | `ai_auto/open_funnel.py` 的 `funnel_wire` | 点首拦截层跳到对应的纪律行 |
| **这个周期值不值得做** | 可交易性判定 + 否决率 + 「换预设解决不了」的明确话术 | `ai_auto/tradability.py` + `discipline_view.strictness_hint` | **一键换周期**（复用 `firstFeasibleAlternative`） |

**第三行是本节的主要新增。** `firstFeasibleAlternative`（`aiTradeTradability.ts:106-113`）今天只服务启动弹窗，把它接到运行期的可交易性卡上即可，前端逻辑几乎为零。需要后端配合的一点是字段：会话状态里的快照类型 `AiTradeTradabilitySnapshot`（`aiTradeTypes.ts:1544-1553`）只有八个字段，没有 `alternatives`；完整的探针响应 `AiTradeTradabilityResponse`（`:1505-1527`）才有。探针本来就会并发算出更长周期的候选（`tradability_probe.py:76-78` 的 `_probe_alternatives`），把这个数组补进会话快照即可，后端无需新增任何计算。

运行期点击这个按钮的语义与启动前不同：启动前只改下拉框（`AiTradeTradabilityFields.tsx:255` 明确写了「不发任何请求」），运行期需要「停止当前会话并以新周期重启」，涉及真实持仓，因此必须走一次显式确认，且确认文案要写清当前持仓会怎么处置。

**首屏的信息层级**（自上而下，三块之间不插入任何其它卡片）：

```text
┌ 我现在赚不赚钱 ────────────────────────────────┐
│ 净额 −xx.x USDT · 32 笔往返 · t = −1.2         │
│ 结论：尚无正期望证据（32 笔已过下限，|t| < 2）       │
│ ▸ 展开：胜率 / 赔率 / 打平所需赔率 / 费用覆盖率     │
├ 为什么没开仓 ──────────────────────────────────┤
│ 意图 48 → 拦截 46 → 委托 2 → 成交 2             │
│ 首拦截层：最小 edge 门禁（41 次）                 │
│ ▸ 点击跳到纪律卡对应行                           │
├ 这个周期值不值得做 ────────────────────────────┤
│ 判定：不可行 · 预计否决 98.6%                    │
│ 换预设解决不了，最宽松档仍会被同一条成本判据拦住     │
│ [ 改用 15m（预计否决约 20.3%）]                  │
└────────────────────────────────────────────┘
```

上图的数字是示意，实际取值全部来自后端下发的读数。三块的顺序刻意与 `AiTradeStatsLive.tsx:184-186` / `:202-204` 已经确立的因果链保持一致：先给结果，再给原因，最后给可执行的动作。

结论行的措辞必须逐字取自后端那张冻结结论表（五个码与中文标题在 `profitability.py:57-63`，判定逻辑在 `:170-182`），前端不得另拟一套。上图第一块对应的码是 `no_edge_yet`「尚无正期望证据」：32 笔已经过了 30 笔下限，分不开的是净期望与 0。它与 `insufficient_samples`「样本不足，不下结论」在界面上长得像，指向的下一步动作却完全不同，前者要去看盈亏比结构，后者只需要继续攒样本。把这两个码混成同一句文案，用户就会在该换周期的时候继续等样本。

**为什么不做自动切换。** `AiTradeTradabilityFields.tsx:255-256` 写明了这条纪律：探针给建议，用户拍板，自动改用户选的参数是本仓库明令禁止的「静默夹紧」形状。运行期涉及真实持仓，这条只会更严格。

**分屏问题的处置**：把三张跨会话卡（盈利体检、校准三问、档位对照）从「历史」标签提到首屏，「历史」标签保留列表与分页。提取时要保留 `AiTradeStatsHistoryList.tsx:49-51` 记录的那个坑：这三张卡必须挂在 `items.length === 0` 的空态早返回**之前**，因为 `/ai-trade/history` 会排除正在运行的那一组，只跑过一组的用户在会话运行期间整页恒空。

**渐进披露原则**：默认给结论，展开才给分母与口径。但有两个例外必须默认可见：样本量（一个 5 笔样本的结论与一个 300 笔样本的结论不能长得一样）与覆盖率（`calibration.py:7-9` 写明 `coverage < 1` 时前端必须把覆盖率显示出来）。

## 四、文案与呈现纪律

**禁用词表**（`profitability.py:31-32` 已用源码正则守门，本篇原样复述并扩展到全部新增文案）：不得出现「已校准」「经回测验证」「预期年化」「稳定盈利」「保证」。

**三条补充**：

1. **任何比例必须与它的分母同屏。** 这条在 `profitability.py:12-15` 是硬约束，`expectancyR` 的分母是 `rSamples`，与 `expectancyUsd` 的 `roundTrips` 不是同一个数，两者不可互相冒充。
2. **覆盖率小于 1 时必须显示覆盖率。** 一个在 8% 子样本上算出来的读数与一个在 100% 样本上算出来的读数并排放着而不说明，本身就是误导（`calibration.py:7-9`）。
3. **后端下发的文案里不写 markdown 粗体。** 后端字符串里的 `**` 在四个渲染点会显示成字面星号，本仓库已复发三次（`track_record.py:19-20`），`tradability.py:19-22` 为同一件事又写了一遍。强调一律用「」。

**「算不出」与「零」必须可区分。** `threshold` 与 `firedCount` 算不出一律显示为空并附说明，绝不填 0 冒充读数（`schemas.py:826-827`）。理由很硬：只报「装配了」而不报「拦了多少」的面板，在「闸门把每一单都拦了」这个最危险的断面上，与「一切正常」长得一模一样。

### 5.2 仓库级实测口径

排除三类不属于一方源码的目录之后，一方**应用**代码共 **15** 个文件超 800 行，一方**测试**共 **9** 个。三类分别是 `desktop/resources/backend/_internal/**`（vendored 依赖）、`tmps/**`、以及 `desktop/.web-build/**`（`apps/web` 的构建产物镜像，已被 `desktop/.gitignore:8` 忽略）。第三类必须排，否则同一批前端文件会被数两遍，结果变成 21 与 13。上表的九个之外还有六个：`services/quant/app/schemas.py` **2494**（一方最大文件，AI-trade 每加一个 wire 键都要改它）、`agent/services.py` 1073、`db/repositories.py` 1029、`apps/web/components/Strategy/StrategyPanel.tsx` 949、`apps/web/app/page.tsx` 885、`okx/trading.py` 844。

其中 `schemas.py` 与 `db/repositories.py` 本轮一定会碰（新 wire 键与决策快照表），须一并纳入净增上限，但**不承诺拆分**。

### 5.3 「不再恶化」的机制

每个提案在文档里声明逐文件净增行数硬上限（[01 号 §四](./01-evidence-layer.md) 已经给了一张），合并前用 `git diff --numstat` 机械核对，超出即判该提案不合格。这个机制的好处是它不需要任何工具支持，坏处是它依赖人执行，因此必须写进 PR 模板的检查项。

超红线文件的**数量**是一条更硬的红线：本轮结束时应用侧仍应是 15 个，多一个即视为回归。

### 5.4 拆分手法

仓库里已经有三次成功的抽取先例，照做即可，不要发明新手法：

| 先例 | 抽出的模块 | 抽取理由（源码原话所在） |
|---|---|---|
| 可交易性预检块 | `AiTradeTradabilityFields.tsx`（335 行） | `:22-24` 明写抽取的唯一理由是 800 行红线，母文件开工前已 1542 行 |
| 纪律自检取数层 | `ai_auto/discipline_runtime.py`（186 行） | `:3-5` 镜像 `CostRuntime` / `ProfitGuardRuntime` / `HorizonRuntime` 的下沉范式，母文件只留三行薄调用 |
| 可交易性取数层 | `ai_auto/tradability_probe.py`（260 行） | `:3-6` 判据在纯核心、取数在运行时层，判据能被纯函数单测钉死 |

三次先例共享同一个形状：**判据与装配下沉到新模块，母文件只留薄调用**。拆 `session.py` 时按这个形状走，每次抽一个运行时门面，母文件的净增恒为负。

拆分 PR 的三条硬约束：不携带任何行为变更；抽取前后的单测全部原样通过，不允许改测试来迁就重构；母文件的净减行数必须大于新模块行数的一半，否则说明只是搬家而没有真正收敛职责。

## 七、风险与回滚

**风险一：档位化会隐藏细粒度控制。** 冻结表 16 个键里有 8 个没有逐项覆盖入口、其中 6 个真的随档位变（见 [02 号 §一](./02-calibration-and-activation.md) 的速查表），把界面进一步收敛会让这个缺口更明显。缓解是保留专家模式：逐字段覆盖入口继续存在，只是默认折叠，并在展开时给出一次确认。

**风险二：首屏聚合可能造成误读。** 把跨会话池化读数与本会话读数放在同一屏，用户很容易把前者当成后者。缓解有两条：每个数字标注它的作用域（本会话 / 跨会话池化）；覆盖率与样本量默认可见，不折叠。`TradabilityCard.tsx:12-14` 已经为一处口径差写过说明文案，新首屏需要同样密度的口径说明。

**风险三：拆文件的回归风险。** 九个文件里 `live_auto/executor.py` 是真实下单路径，`session.py` 是决策中枢，两者都没有可以一次性验证的等价性测试。缓解是按优先级从低风险的类型文件与前端组件开始，每次只拆一个，且拆分 PR 里不允许携带任何行为变更。

**自我反驳**：本篇的产品改造不会让系统变得更赚钱，它只让用户更早知道系统赚不赚钱、以及为什么。如果 [00 号](./00-overview-and-rediagnosis.md) 的结论成立，本篇最有价值的产出是那个运行期的「一键换周期」按钮，因为它把仓库里已经算出来但没人看得见的那个结论（`discipline_view.py:139-144` 的 `_infeasible_hint`）接到了一个真实动作上。其余部分都是可解释性的改善，重要但不改变期望值。

**回滚路径**：本篇的改动全部在展示层，不新增任何决策路径上的判定。首屏改造若造成误读，回滚就是把三张卡放回「历史」标签；一键换周期若被误触，它本身带二次确认，且只在用户显式点击后才停止会话。所有后端读数在回滚后仍在 wire 上，不会丢失。

**交叉阅读**：首屏第三问所依赖的判定见 [00 号 §二](./00-overview-and-rediagnosis.md) 的 N-1，档位数字的来历见 [02 号 §二](./02-calibration-and-activation.md)，标定记录的产出流程见 [03 号 §五](./03-verification-and-gates.md)，新增数据面的展示落点见 [01 号](./01-evidence-layer.md)。
