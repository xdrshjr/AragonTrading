# 06 · 离线评估与上线闸门

**本篇结论先行**：**改什么**：在 01~05 的任何参数变更进入实盘之前，加设五道离线闸门，并把「回测能证明什么」这件事本身规定清楚。**为什么**：本仓库的 AI 回测与实盘**决策链结构性不同构**——回测硬编码 `allow_limit=False`（`services/quant/app/ai_auto/backtest.py:232,240`）、`reflection_enabled` 默认 `False`（`backtest.py:130`），而实盘这两个总闸默认均为 `True`（`services/quant/app/config.py:163,135`）。不对齐就跑闸门，等于在验证另一个系统（D-14）。**验收看什么**：闸 0 的对账表必须逐项一致，闸 1~闸 4 全绿才允许上线，任一不过即阻断。

## 一、问题定位

**D-14（回测不可外推）**：仓库自己已经把 AI 回测的六条已知偏差逐条写在 `backtest.py:91-102` 的 `_PROFIT_GUARD_BACKTEST_NOTE` 里，且与前端文案同源：① 同一根内的新高不会立即抬高移动止盈线；② 跳空穿越按开盘价成交；③ 回测按根推进而实盘每 5 秒盯市；④ 无部分成交、无挂单撤改、无交易所降级态；⑤ 开仓当根不判回撤，且冷却秒数短于一根 K 线时在回测里几乎恒于次根即已过期；⑥ 承诺退出线同为 bar 内极值保守近似，且回测里的 `holdExitPx` 来自回测 LLM，与实盘模型可能不同。

**在这六条之上还有第七条，且比前六条更致命**：回测与实盘的 `allow_limit` 与 `reflection_enabled` 默认值不同构。前六条是**精度**问题（回测比实盘保守），第七条是**结构**问题——回测跑的根本不是实盘那条决策链。`SimBroker` 每单必成、无部分成交（`services/quant/app/engine/simulator.py:103-109` 的费率与滑点是固定 bps 假设），叠加这条结构差异，回测结论对实盘的外推价值极低。

**D-15（缺显著性口径）**：`_compute_ai_stats`（`services/quant/app/ai_auto/session.py:1357-1404`）产出的是动作计数、观望占比、平均置信度、降级数与四个反思计数，没有 t 值也没有净期望。因此即便回测跑出正收益，也无法回答「这是运气还是 edge」。

## 二、目标与不做什么

**目标**：① 用闸 0 消除回测与实盘的结构差异，让比较有意义；② 用 purged / embargo walk-forward 把信息泄漏挡住；③ 用成本敏感性与决策重放证伪参数的稳健性；④ 用纸面灰度把模型假设与真实撮合对账。

**不做什么**：① **不用回测宣称正期望**——回测只用于**排除明显负期望**，这是本篇的核心纪律；② 不为闸门新建第二套回测引擎，全部复用既有 `run_backtest` / `SimBroker` / AI 回测运行器；③ 不在闸门里放宽任何既有安全约束（平仓/撤单永不被拦、总闸默认关即逐字回退）。

## 三、方案设计

### 3.1 闸 0：链路同构性对账（第 0 道，最先跑）

闸门报告的**第一张表**必须是逐项对账，任一「不同构」即阻断后续闸门：

| 配置项 | 回测当前值 | 实盘默认值 | 对齐要求 |
|---|---|---|---|
| `allow_limit` | `False`（`backtest.py:232,240`） | `True`（`config.py:163`） | 闸门运行时须显式对齐；无法对齐则报告中标注结论仅对 market-only 链路有效 |
| `reflection_enabled` | `False`（`backtest.py:130`） | `True`（`config.py:135`） | 必须对齐为 `True` 后再跑 |
| 利润保护 | 回测总闸 `ai_trade_profit_guard_backtest_enabled=True`（`config.py:249`） | `True`（`config.py:217`） | 已同构，记录即可 |
| 共识门禁 | 随 `ai_trade_min_consensus` | `0`（默认关，`config.py:145`） | 已同构 |
| edge 门禁（新增） | 须插在语义等价位置 | 共识后、反思前 | 位置不同构即阻断 |

### 3.2 闸 1：purged / embargo walk-forward

仓库已有 `plan_walk_forward_windows`（`services/quant/app/engine/backtester.py:26`，服务层调用在 `services/quant/app/agent/services.py:914,984`）与窗口数硬上限 `walk_forward_max_windows = 200`（`config.py:287`）。**但 purge 与 embargo 在全仓库零实现，属本计划新增，不得写成「复用」。**

purge 的作用是剔除训练集中与测试集标签窗口重叠的样本（triple-barrier 的标签跨多根，重叠即泄漏）；embargo 的作用是在测试集之后再空出一段，防止序列自相关把信息带回训练集。

| 参数 | 默认值 | 取值依据 |
|---|---|---|
| `purge_bars` | `triple_barrier_max_bars` = 24 | 必须 ≥ 标签的最长持有期，否则泄漏必然发生 |
| `embargo_bars` | 12 | 取 purge 的一半；加密日内自相关衰减快，半个标签窗口足够 |
| `min_test_trades` | 30 | 少于 30 笔的窗口不产出结论，只记录 |

**判据**：全部窗口的净收益（扣 [01](./01-交易成本与执行质量.md) 的成本）中位数 > 0，且为正的窗口占比 ≥ 60%。

### 3.3 闸 2：成本敏感性

把成本模型的 `totalBps` 乘以 1.5 重跑闸 1，净收益中位数仍 > 0 才算通过。依据：实测滑点与模型滑点的偏差阈值是 3 bps（[07](./07-实盘可观测与归因.md)），叠加费率档位变动与资金费率极端值，1.5 倍是一个能覆盖多数不利情形的保守系数。

### 3.4 闸 3：决策重放一致性

同一批历史 payload 分别喂给改造前后的决策链，比较：① 动作一致率；② EV 分布的漂移。**开仓率骤降为 0 是明确的回滚触发条件**（对应 [02](./02-信号层重构与元标签.md) / [04](./04-决策智能体改造.md) 的双重计费风险）。

| 判据 | 阈值 | 不达标处置 |
|---|---|---|
| 动作一致率 | 50%~90% | < 50% 说明改动过猛，> 90% 说明改动没生效 |
| 开仓率 | 不得为 0，且不低于改造前的 30% | 为 0 立即判定双重计费，阻断 |
| EV 分布 JS 散度 | < 0.3 | 超阈需人工复核分布右移是否为凑数行为 |

### 3.5 闸 4：纸面灰度

在 paper 路径跑满 `paper_gate_trades = 50` 笔，比较实测滑点与模型滑点、实测限价成交率与假设值。**注意纸面路径本身也按 `default_taker_fee_bps` / `default_slippage_bps` 计费（`services/quant/app/paper/session.py:60-61`）**，因此它验证的是撮合逻辑与成交率，不是真实费率——真实费率只能由实盘的 A0 回执给出。

### 3.6 champion-challenger

新参数集以 challenger 身份与 champion 并行跑纸面，连续 `challenger_min_trades = 100` 笔净期望优于 champion 才允许换位。**任何时刻只有一套 champion 参数在实盘生效**，避免多套参数同时改动导致归因失效。

## 四、与现有代码的接入点

## 五、验收指标与门禁

| 闸 | 判据 | 采样窗口 | 不达标处置 |
|---|---|---|---|
| 闸 0 | 对账表逐项一致 | 每次闸门运行 | 阻断后续全部闸门 |
| 闸 1 | 净收益中位数 > 0 且正窗口占比 ≥ 60% | ≥ 8 个 walk-forward 窗口 | 阻断上线，回到参数标定 |
| 闸 2 | 成本 ×1.5 后中位数仍 > 0 | 同闸 1 | 上调 `k_min` 后重跑；仍不过则该参数集作废 |
| 闸 3 | 一致率 50%~90% 且开仓率不为 0 | 200 条历史 payload | 开仓率为 0 立即判定双重计费 |
| 闸 4 | 实测滑点与模型偏差 < 3 bps | 50 笔纸面 | 重估成本模型 |
| champion 换位 | challenger 净期望连续 100 笔占优 | 滚动 100 笔 | 不换位，challenger 继续观察 |

**纪律条款（写进闸门报告首页）**：本仓库的回测由于上述七条偏差，**只能用于排除明显负期望的参数集，不能用于宣称任何参数集具有正期望**。闸 1~闸 3 全绿只代表「没有被证伪」，正期望的唯一证据来自实盘 A0 落地后的滚动净期望统计。

## 六、风险与回滚

**自我反驳一（必须写明）**：**闸门本身可能成为过拟合的通道。** 反复用同一批历史数据跑闸门、按结果调参、再跑闸门，本质上是把测试集变成了训练集——闸门跑得越多，通过率越高，而外推能力越差。缓解：记录每个参数集的闸门运行次数，同一参数族运行超过 `gate_runs_per_family = 5` 次即强制换用新的样本外区间；闸门报告必须显示累计运行次数。

**自我反驳二**：**闸 0 可能根本无法对齐。** `allow_limit` 在回测里恒为 `False` 是有原因的——`SimBroker` 的挂单模型是「次根成交」的简化，与实盘的 `resting.py` 三态状态机不同构，强行对齐只会制造一个假的一致性。若判定无法对齐，正确动作是**在报告中明确标注结论仅对 market-only 链路有效**，而不是伪造对齐。这会削弱闸 1~闸 3 的说服力，但诚实的弱结论优于虚假的强结论。

**自我反驳三**：五道闸会显著拉长每次参数变更的周期（闸 4 的 50 笔纸面在 15m 周期上可能需要数天）。若这个周期长到团队开始绕过闸门，闸门就失去了意义。缓解是把闸 0~闸 3 做成可在数分钟内跑完的自动化步骤，只有闸 4 需要真实时间；紧急修复（如 A0 的记录步骤）允许只过闸 0 与闸 3。

**回滚路径**：闸门是离线工具，不参与实盘执行路径，因此无需回滚开关——关闭闸门只意味着回到当前「无闸门」状态。真正需要回滚的是被闸门放行的参数，其开关清单见 [08](./08-实施路线图与里程碑.md)。
